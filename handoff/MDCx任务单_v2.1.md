## 0. 要解决什么

用户 10-18 发现：主界面右侧「成功」列表里，**每一条都带分辨率后缀，即使没有开启分辨率后缀也一样**。（用户口述，没有截图。）

我们要先知道三件事，才能决定要不要改代码：

1. 这个后缀是哪段代码拼出来的；
2. 它到底受哪几项配置控制，还是根本不受配置控制；
3. 它只是列表上的显示，还是连实际落盘的文件名/文件夹名也带了。

## 3. 要回答的问题（逐条回答，每条带证据）

**Q1 列表文字是哪里生成的**：主界面右侧「成功」列表的每一条文字，从「一条影片刮削成功」到「文字出现在列表里」，经过哪些文件和函数？列出路径和行号，写出最终拼接这条文字的那一行代码。

**Q2 后缀的来源与条件**：
- 这条文字里的分辨率后缀（如 1080P、4K 一类）具体是哪个变量、哪段代码加上去的？
- 把代码里所有会影响它的配置项列成表：配置项名 → 它的作用 → 代码位置（路径 + 行号）。必须包含对 §1 里每一项的结论（「有影响」或「无影响」）。
- 加后缀的那段代码有没有任何「配置没开就不加」的判断？有就贴出条件，没有就明确写「无条件」。

**Q3 结论三选一**：
- A 由配置控制，用户的配置里对应开关其实是开着的（写出是哪一项）；
- B 不受任何配置控制，永远加（代码行为，属设计或缺陷，写出依据）；
- C 无法确定（说明卡在哪）。

**Q4 显示 vs 落盘**：列表上带的后缀，和实际写到磁盘上的文件名、文件夹名是同一个来源吗？
- 找出重命名文件和文件夹时拼名字的代码（路径 + 行号），说明里面有没有同样的后缀逻辑，受哪些配置项控制。
- 结论二选一：A 只是列表显示，落盘名不受影响；B 落盘名也带，且与列表一致；C 无法确定。

**Q5 来源追溯**：`git log -S` 或 `git blame` 查，加后缀的那几行是 fork 前（上游 sqzw-x/mdcx、Hazard804/mdcx）就有的，还是本仓库 v1.7 及以后改动引入的？写出提交号和日期。需要更多历史时用有界 fetch（`git fetch --depth=1000 origin master`），不要 `--unshallow`。

**Q6 机械验证（本地离线，强烈建议做）**：在仓库**之外**的临时目录写脚本，不联网，直接调用 Q1 找到的那段生成列表文字的代码，用一条假的刮削结果数据（任意番号、已知分辨率），按下面的矩阵各跑一次，每次只改一个配置项，其余保持 §1 的值：

| 组 | 改动 | 记录 |
|---|---|---|
| 基线 | §1 的值，一项不改 | 生成的列表文字 |
| 1 | 只把 `file_hd` 改为 `false` | 同上 |
| 2 | 只把 `folder_hd` 改为 `false` | 同上 |
| 3 | 只把 `mark_type` 去掉 `"hd"` | 同上 |
| 4 | 只把 `suffix_sort` 去掉 `"definition"` | 同上 |
| 5 | 只把 `hd_name` 改为另一个合法值（读代码找出合法值） | 同上 |

再加一组「Q2 里找到的其他相关项」各改一次（如有）。汇报里贴：每组的输入配置差异、输出文字、与基线是否不同。脚本本身贴进汇报附录，不提交进仓库。做不了（函数与界面耦合太深）就说明卡在哪，**不要**为了能测而改代码。
